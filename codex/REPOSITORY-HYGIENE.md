# Repository Hygiene

**Status:** Authoritative Repository Governance

**Epic:** CEM-R – Repository Governance

**Engineering Asset:** EA-R039 – Repository Hygiene Governance

---

# 1. Purpose

Repository Hygiene establishes the authoritative governance governing repository contents, repository cleanliness, repository participation, and repository tracking policy.

Repository Hygiene defines what may participate in authoritative repository state while preserving Repository Mutation as the exclusive operation authorized to modify repository contents.

Repository Hygiene governs repository inclusion and exclusion only.

It does not perform repository mutation or source-control operations.

---

# 2. Objectives

Repository Hygiene shall:

- establish deterministic repository participation;
- classify every repository-resident artifact;
- govern repository inclusion and exclusion;
- govern repository cleanliness;
- govern repository tracking;
- govern `.gitignore`;
- preserve repository integrity;
- preserve repository addressability;
- preserve deterministic engineering evidence chains.

---

# 3. Architectural Principles

Repository Hygiene is founded upon the following principles:

1. Every repository artifact shall possess exactly one hygiene classification.
2. Repository participation shall be deterministic.
3. Repository exclusion shall be deterministic.
4. Repository cleanliness shall be continuously maintained.
5. Repository Mutation remains the exclusive repository-state modification operation.
6. Repository Hygiene introduces no engineering decisions during execution.

---

# 4. Repository Artifact Classifications

Every repository-resident artifact shall belong to one of the following classifications.

## Repository Assets

Authoritative repository content.

Examples include:

- governance documents;
- engineering documentation;
- engineering records;
- approved source code;
- approved repository assets.

Repository Assets are version controlled.

---

## Generated Artifacts

Artifacts deterministically produced from Repository Assets.

Examples include:

- generated documentation;
- generated reports;
- generated diagrams;
- generated exports.

Tracking is governed by repository policy.

---

## Transport Artifacts

Artifacts used only to transport repository state.

Examples include:

- working ZIP archives;
- exported repository packages;
- staging bundles;
- release archives.

Transport Artifacts are excluded from authoritative repository state unless explicitly approved.

---

## Workspace Artifacts

Developer-local artifacts.

Examples include:

- editor settings;
- local configuration;
- user preferences;
- temporary workspace files.

Workspace Artifacts are excluded.

---

## Tool Artifacts

Artifacts generated by development tooling.

Examples include:

- virtual environments;
- caches;
- package metadata;
- test caches.

Tool Artifacts are excluded.

---

## Build Artifacts

Artifacts produced by build operations.

Examples include:

- compiled binaries;
- intermediate output;
- packaged deliverables;
- generated execution artifacts.

Build Artifacts are excluded unless explicitly approved.

---

## Temporary Engineering Artifacts

Artifacts supporting transient engineering execution.

Examples include:

- scratch files;
- temporary reports;
- patch staging;
- comparison outputs;
- engineering working files.

Temporary Engineering Artifacts are excluded.

---

# 5. Repository Inclusion Policy

Repository Assets shall be tracked.

Generated Artifacts shall follow repository policy.

Transport Artifacts shall not be tracked unless explicitly approved.

Workspace Artifacts shall not be tracked.

Tool Artifacts shall not be tracked.

Build Artifacts shall not be tracked.

Temporary Engineering Artifacts shall not be tracked.

---

# 6. Repository Exclusion Policy

Repository exclusion shall be implemented exclusively through the repository's `.gitignore`.

No exclusion policy shall exist outside approved Repository Hygiene Governance.

---

# 7. .gitignore Governance

The repository `.gitignore` is the implementation of Repository Hygiene exclusion policy.

It shall:

- organize ignore rules into governed sections;
- correspond to Repository Hygiene classifications;
- exclude all approved non-tracked artifact classes;
- prevent accidental repository mutation by tooling;
- remain deterministic.

Ad hoc ignore rules are prohibited.

---

# 8. Repository Cleanliness

A repository is considered clean when:

- tracked artifacts accurately represent repository state;
- ignored artifacts conform to Repository Hygiene;
- unintended tracked modifications are absent;
- repository classifications remain valid.

Repository cleanliness is required before:

- Repository Mutation;
- Repository Mutation Verification;
- Repository Closeout;
- Commit Readiness;
- Commit.

---

# 9. Repository Hygiene Validation

Repository Hygiene Validation verifies:

- artifact classification;
- repository participation;
- repository exclusion;
- repository cleanliness;
- repository tracking consistency.

Validation does not modify repository state.

---

# 10. Authority Boundaries

Repository Hygiene governs:

- repository participation;
- repository inclusion;
- repository exclusion;
- repository cleanliness.

Repository Hygiene does not govern:

- engineering decisions;
- repository mutation;
- source-control operations.

Repository Mutation remains the exclusive repository-state modification operation.

Repository Operations Governance remains responsible for Commit, Tag, Push, and Release.

---

# 11. Producer–Consumer Relationships

Repository Hygiene participates in the engineering lifecycle as follows:

Repository Patch Update Verification
        │
Repository Asset Generation
        │
Repository Asset Verification
        │
Repository Mutation
        │
Repository Mutation Verification
        │
Repository Hygiene Validation
        │
Repository Closeout
        │
Commit Readiness
        │
Commit
        │
Tag
        │
Push
        │
Release

Repository Hygiene validates repository participation without altering existing producer–consumer relationships.

---

# 12. Execution Invariants

Repository Hygiene shall:

- preserve Repository Mutation authority;
- preserve Repository Operations Governance;
- preserve repository addressability;
- preserve repository traceability;
- preserve deterministic producer–consumer evidence chains;
- introduce no execution-time engineering decisions.

---

# 13. Compliance

Repository Hygiene compliance requires:

- approved artifact classification;
- approved repository participation;
- deterministic exclusion policy;
- governed `.gitignore`;
- repository cleanliness;
- successful Repository Hygiene Validation.

Only compliant repositories may proceed to Commit Readiness.

---

# 14. Governance Summary

Repository Hygiene establishes the authoritative governance governing repository contents.

Repository Mutation modifies repository state.

Repository Operations Governance manages source-control operations.

Together these governance assets preserve deterministic, auditable, and reproducible repository evolution.
